# Muhasebi — notes for AI assistants

SaaS for mobile-phone parts/accessories/repair shops in Egypt. Product plan: `PLAN.md`. Technical plan: `TECH_PLAN.md`. UI copy is Egyptian Arabic, RTL.

## Layout
- `apps/api` — Laravel 13, PHP 8.4, PostgreSQL. Modular monolith under `app/Modules/*`, shared kernel in `app/Support/*`.
- `apps/web` — Nuxt 4 SPA (`ssr: false`), Nuxt UI 4, Pinia. Talks to `/api/v1` with a Sanctum bearer token.

## Rules that tests enforce (`apps/api/tests/Architecture`)
- A module may only reference another module's `Contracts\` and `Events\` namespaces.
- Every model under `app/Modules/*/Models` uses `BelongsToTenant` (one shop) or `SharedBetweenTenants` (rows owned by two shops, e.g. inter-shop orders), except the allowlist (Tenant, User).
- Every route of an `Optional` module carries `module:{key}` middleware.
- Every signed-in API route checks a permission: `can:` middleware, a Form Request with its own `authorize()`, or an `abort_unless(...->can(...))` in the action (`RouteAuthorizationTest`; the few exceptions are listed there).

## Conventions
- New module: create `app/Modules/{Name}/module.php` returning a `ModuleManifest`; routes in `routes.php` (auto-prefixed `/api/v1`), migrations in `Database/migrations`, listeners registered via a `ModuleServiceProvider` `$listen` array.
- Cross-module side effects: if it must succeed with the change → call a `Contracts\` interface inside the transaction; otherwise → `EventRecorder::record(new SomethingHappened(...))` and a `ModuleListener` elsewhere.
- Permissions are declared in module manifests (`permissions: ['key' => 'Arabic label']`) and enforced with `can:{key}` route middleware / `$user->can()`. Owners have every permission of the modules the shop can use; others get their role's permissions ∩ usable modules (`Identity\PermissionResolver`). Owner-only screens use the `owner` gate.
- Routes that act inside a branch add the `branch` middleware and read `Support\Tenancy\CurrentBranch` (from the `X-Branch-Id` header).
- Sensitive actions call `Support\Audit\Auditor::record()` inside their transaction (shows in سجل العمليات).
- Controllers are thin: Form Request → Action → API Resource. Business rule failures throw `DomainRuleException` (rendered as `{message, code}`).
- Money is stored as integer piasters. IDs for shop data are UUIDv7 (`HasUuids`).
- Don't cache Eloquent models (Laravel 13 cache refuses to unserialize objects); cache arrays.
- Other shops' public info (name, code, phone) comes from `Identity\Contracts\ShopDirectory`, never from Identity's models.
- UI follows design direction A (`docs/design/option-a-*.png`): theme tokens in `apps/web/app/assets/css/main.css`. Dates/numbers use Latin digits (`ar-EG-u-nu-latn`, `.num`).
- Catalog: what is sold/stocked is a `ProductVariant` (own barcode, prices in piasters); compatibility (`device_model_product`) is per product. Text search goes through `Support\Text\SearchText` (Arabic normalisation: أإآ→ا، ة→ه، ى→ي) against stored `search_name` columns with `pg_trgm` indexes; `Product::search()` ANDs the words across name, SKU, barcode, brand and compatible models. New shops get `DefaultCatalog` via `TenantRegistered`. Every selling-price change writes the append-only `price_changes` (`Catalog\Support\PriceHistory`, from the product form or a bulk edit); bulk edits (`/products/prices`, `BulkPriceAction` + `PriceRule`: percent / amount / fixed price from a price field or the branch's average cost, rounding) preview first, then apply with an audit entry.
- Stock: only through `Inventory\Contracts\StockLedger` (`receive` = new lot + weighted `avg_cost`; `issue` = FIFO over lots, may go negative and is then costed at `avg_cost`), called inside the caller's transaction. `stock_movements` is append-only; `stock_levels`/`stock_lots` are balances locked per (branch, variant). Stock is per branch (`branch` middleware). Other modules read variants via `Catalog\Contracts\VariantCatalog`, never Catalog models. Costs are shown only with `products.view_cost`. IMEI / serials (products with `track_serial`): `Inventory\Contracts\SerialRegistry` (`receive` / `issue` / `takeBack`, next to the StockLedger call with the same `StockReference`; `serial_numbers` = where each unit is now, append-only `serial_events`); a line needs one serial per unit (`SerialCount::check`) on purchases, sales and their returns, stored on the line's `serials` and printed on the receipt. A serial never received (opening stock, older stock) is registered as it's sold. Adjustments and counts (`AdjustStockAction`) need the serials of the difference (the extra units received, the missing ones issued); opening stock takes them optionally (one per unit when given); repair parts need theirs (`repair_ticket_parts.serials`, issued as `RepairUse`, `takeBack` on removal). The web asks with `InventorySerialsInput` wherever the row / price-check item has `track_serial`. Lookup `GET /inventory/serials?q=` (`/inventory/serials`); the POS adds a unit by scanning its IMEI.
- Purchases (Suppliers module): `CreatePurchaseAction` receives each line into stock at its cost after the invoice discount and posts the total to the supplier account; `SupplierAccount::post()` keeps `suppliers.balance` (> 0 = the shop owes) and the append-only `supplier_transactions` in step under a row lock. What is paid now (and `/suppliers/{id}/payments`) comes out of the user's shift drawer via `CashDrawer` (`DrawerEntry::SupplierPayment`, negative amount; bank transfers never, `from_drawer: false` for money from the safe). Returns issue from the purchase's own lot (`StockLedger::issue(..., fromLotId:)`). Per-shop document numbers come from `Support\Numbering\DocumentNumbers` inside the creating transaction. Ledgers order by their `seq` identity column, never by timestamps.
- Sales (POS): `CompleteSaleAction` prices lines from the catalog (`VariantSummary::priceFor(level)`), issues stock FIFO and stores each line's `unit_cost`; the client sends the sale `id` (the cart id) so a retried checkout is saved once. Only cash gives change. Returns refund each unit's share after the invoice discount and restock sound units at the line's cost. Receipts have a `public_token` → public page `/r/{token}` (QR on the receipt, WhatsApp share); pages opt out of login with `definePageMeta({ public: true })`.
- Cash (Cash module): selling needs the cashier's open shift (`cash_shifts`, one open per user per branch). Money moves only through `Cash\Contracts\CashDrawer::record()` inside the caller's transaction (cash always needs an open shift; card/wallet join one if open); `cash_movements` is append-only. Expenses / deposits / withdrawals are cash on the user's shift; closing stores expected vs counted per method. Shift numbers `SH-00001`.
- Customers: `customers.balance` (> 0 = owes the shop) and the append-only `customer_transactions` move together under a row lock (`CustomerLedger`). Credit (آجل) is the `credit` sale payment method: needs a customer and `customers.credit`, respects `credit_limit` via `Customers\Contracts\CustomerAccounts::chargeSale()`; a return with `refund_method: credit` goes back to the account. Phones are stored E.164; show them with `localPhone()`.
- Customer privacy (Law 151/2020): consent to keeping their data is recorded on the customer (`data_consent` true/false/null = never asked, `_at`, `_by_name`) from the pre-ticked `CustomersConsentCheckbox` on the customer form (POS picker too) and repair intake (`consent` → `CustomerAccounts::findOrCreate`). Erasure (`POST /customers/{id}/erase`, owner; `EraseCustomerAction`) refuses a non-zero balance or open tickets, then anonymises: name «عميل محذوف» (`Support\Privacy\Anonymised`), no phone/notes, inactive, `erased_at`; the drawer notes (`CashDrawer::redactNotes`) and audit descriptions (`Auditor::redact`) lose the name in the transaction; `Customers\Events\CustomerErased` (a keyed `PhoneFingerprint`, never the number) lets each module anonymise its copies (Sales, Repairs incl. unlock code and IMEI, Messaging) with listeners that set `evenWhenModuleDisabled()`. A module holding a customer's name/phone must add such a listener. Export (`GET /customers/{id}/export`, customers.manage) is JSON from `Sales\Contracts\CustomerSales` / `Repairs\Contracts\CustomerRepairs`. Retention: `customer_privacy_settings.retention_years` (owner, 1–10, off by default) and the daily `customers:erase-inactive` go through the same action. Public notice: `/privacy`.
- Repairs: a `RepairTicket` (per branch, `RP-00001`) goes received → diagnosing → awaiting_approval → repairing → awaiting_part → ready / rejected (`TicketStatus::next()`), then `DeliverTicketAction` settles it (change from cash only; credit via `CustomerAccounts::chargeRepair`; a deposit larger than the bill is refunded) and starts the warranty. Every change writes the append-only timeline (`Support\Timeline`). Money goes through `Support\TicketMoney` → `CashDrawer` (`DrawerEntry::Repair`); parts leave stock with `MovementType::RepairUse` and come back with `RepairReturn`. Faults are snapshots of the shop's editable lists. The unlock code is encrypted and only returned with `repairs.update_status`. Public tracking: `/t/{token}` (API `public/repairs/{token}` resolves the shop via `ResolveTicketShop`). WhatsApp text per status: the `repair_{status}` message template. Technician commission: per-technician `CommissionRule` (percent of labor-after-discount or of profit, or fixed per device), fixed on the ticket at delivery (`Support\Commission`; none for warranty returns); shown to that technician and to `reports.profit`. The repairs report (`Reports\Definitions\RepairsReport`) groups by technician, fault or model.
- Messaging: WhatsApp texts are templates (`Messaging\Support\Templates`: key, variables, built-in wording; the shop's rewording in `message_templates`, edited at `/settings/templates` with `messages.templates`). The web fills them with `useMessages()` (`renderTemplate`: `{name}` → value, a line whose variable is empty is dropped) and every send is logged in the append-only `message_logs` (`POST /messages/log`, `messages.send`). Other modules ask `Messaging\Contracts\MessageHistory::lastSent()`; repairs uses it for ready devices whose customer wasn't told (`ready_notified_at`, summary `unnotified`).
- Partner repairs: a ticket can go to a partner shop (`OutsourceTicketAction` → `ShopOrders\Contracts\PartnerRepairs::send`, a `repair` shop order; `outsourced_*` on the ticket, can't be delivered until the partner hands it back, the partner's price is `outsource_cost`, counted in profit and commission via `RepairTicket::cost()`). `Repairs\Listeners\SyncPartnerRepairs` on `ShopOrderUpdated`: the sender's ticket follows the order; the partner accepting opens a ticket per device (`partner_order_id`, the sending shop as customer, main branch), and `Support\PartnerSync` moves the order (preparing / ready / delivered with each device's bill as its price) as those tickets move. Repairs is shown to accessories and phone shops too (`trialFor: ['repair']`: only repair shops start on it).
- Notifications (core module, the top-bar bell `NotificationBell`): one `notifications` row per shop (title, body, icon, `to` web link, optional `permission` — only users who `can()` it see it) and per-user read marks in `notification_reads`. Filled by `ModuleListener`s in the Notifications module on other modules' events, only for what the OTHER shop did (`ShopOrderUpdated::$actorTenantId`); today `NotifyPartnerActivity` (partnership requests, new orders / repair jobs, the partner moving an order → `/shop-orders/{id}`). API `GET /notifications` (unread first, newest first; `meta.unread`), `GET /notifications/unread`, `POST /notifications/{id}/read`, `POST /notifications/read-all` (own-account routes, listed open in `RouteAuthorizationTest`). The web polls the count every 60s and on window focus. Icons sent by the API go in `icon.clientBundle.icons`.
- Printing: wrap printable output in `<PrintSheet page-size margin>` and trigger with `usePrint()`; `@media print` shows only `.print-root`. Receipts (`PrintReceipt`, 80mm) and labels (`ProductLabel`, sized in mm; `/products/labels`) use `PrintBarcode` (EAN-13 when valid, else CODE128) and `PrintQrCode`. In-store barcodes are EAN-13 with prefix `2` (`GenerateBarcodesAction`).
- Dashboard: `/sales/stats` (reports.view; profit only with reports.profit) feeds the home page; charts use ECharts via `components/dashboard/*`, colours read from the `--app-chart` / `--ui-*` tokens and re-read on theme change, with a table view. Quick actions live in `composables/useQuickActions.ts` (home tiles + Ctrl+K). Icons named only in `.ts`/script code must be listed in `icon.clientBundle.icons` — the scan misses them.
- Reports module: read-only SQL over the other modules' tables (never their models). Each report implements `Reports\Support\Report` and returns a `ReportResult` (summary, typed columns, rows, totals, optional chart); register it in `ReportRegistry`. One page (`/reports/[key]`), the `.xlsx` export (`XlsxReport`) and the A4 print layout (PDF via the browser) serve every report. Profit needs `reports.profit`, costs `products.view_cost`; branches come from `Identity\Contracts\BranchDirectory`.
- Modules whose screens aren't built yet have `available: false` in their manifest: `ModuleAccess::enabled()` is false for them whatever the shop's row says (no menu, permissions, routes), trials can't start (`module_coming_soon`; registration skips them so the trial isn't burnt) and the modules page shows «قريباً». A single unbuilt screen: `new MenuItem(..., ready: false)`.
- Shop types: a shop picks one or more `Identity\Enums\ShopType` (accessories, repair, phones, wholesale, importer; stored in `tenants.shop_types`, `shop_type` = the first; the old `accessories_repair` reads as both) at registration (`/shop-types` feeds the form) or later on the modules page (`PUT /shop/types`, owner). Optional modules declare `shopTypes` in their manifest: those matching start on trial at registration, the modules page lists only modules for the shop's types (empty `shopTypes` = every shop) plus any it already uses. Other modules read the types via `Identity\Contracts\ShopProfile`.
- Quick price check (استعلام سعر): `GET /inventory/price-check?q=` (products.view; wholesale/technician prices with sales.discount or products.manage, cost with products.view_cost, stock per branch with inventory.view), opened by `usePriceCheck().show()` — top bar, F8, Ctrl+K, home tile. Quick actions may `run` something instead of `to` a page.
- Billing (subscriptions): plans / module prices in `config/billing.php` (piasters, VAT included). Each shop has a `Subscription` (14-day trial, then `paid_until`); `SubscriptionStatus::of()` derives trialing / active → past_due (7 days) → restricted (no POST products, import, users, branches) → suspended (read-only; billing and auth still work), applied to every shop request by `Billing\SubscriptionGuard` through the `Support\Tenancy\TenantRequestGuard` hook in `ResolveTenant` (402 `subscription_*`). Payment = InstaPay: the owner sends a `PaymentRequest` (reference + proof on the local disk) from `/settings/billing`; a platform admin approves it (or activates a shop directly) → `Subscriptions::activate()` writes a `BillingInvoice` (INV-YYYY-NNNNNN, VAT inside), extends from the end of the current period and grants the plan's modules via `ModuleManager\Contracts\TenantModules`. Platform admins are `PlatformAdmin` (own Sanctum tokens with the `admin` ability, expiring after `ADMIN_TOKEN_HOURS`; `can:platform-admin`; `php artisan billing:admin email name`); their API is `/api/v1/admin/*` behind `Billing\Http\Middleware\AdminGate` (only on `ADMIN_DOMAIN`, optional `ADMIN_ALLOWED_IPS`, else 404), login needs password + an authenticator code (TOTP via `Support\Security\Totp`, set up only from the shell: `billing:admin-2fa`; no code set up = no sign-in) and locks after 5 wrong tries, every action goes to the append-only `platform_admin_actions` (`AdminLog`). Their UI is a separate Nuxt app, `apps/admin` (own domain, strict CSP with build-time script hashes from `scripts/csp.mjs`), never shipped in `apps/web`. Shops are listed for them via `Identity\Contracts\PlatformShops`.
- Menu entries come from module manifests (`new MenuItem(to, label, icon, permission, group: 'sales'|'stock'|'services'|'reports'|'settings')`); the sidebar groups them by `group` (titles in `apps/web/app/utils/navigation.ts`). Add new icons to `icon.clientBundle.icons` in `apps/web/nuxt.config.ts`.
- Account security (Identity): two-factor sign-in is TOTP (`Support\Security\Totp`, RFC 6238, ±1 step, a used step is refused) via `Identity\Auth\TwoFactor` — encrypted `two_factor_secret`, SHA-256 hashed one-time recovery codes; `account/two-factor` setup (password) → confirm (code) → disable (password + code). With it on, `POST /auth/login` returns a 5-minute `challenge` (`LoginChallenges`, cache, 5 tries, throttled) that `POST /auth/two-factor` swaps for a token. Signed-in devices are Sanctum tokens issued by `DeviceSessions::issue()` (device name from the client, IP, user agent); `account/sessions` lists / revokes / logs out the others, the owner does the same for staff at `users/{user}/sessions` (and can reset an employee's 2FA). Screen: `/settings/security`; owners without 2FA are nudged on the home page. Own-account routes are in `RouteAuthorizationTest::OPEN`.
- Light and dark themes: colours only through the `--ui-*` / `--app-*` tokens in `main.css` (`:root` and `.dark`), never hard-coded. Default is light; the top bar switches light / dark / follow device.

## Deployment
- `infra/production/`: Docker Compose stack (Caddy edge with auto-HTTPS serving the Nuxt static build and proxying `/api` to FrankenPHP; Horizon worker, scheduler, Reverb, Postgres 17, Redis). `init.sh` once, `deploy.sh` per update, `backup.sh`/`restore.sh`. Guide: `docs/DEPLOY.md`. On a server whose nginx already owns 80/443, `COMPOSE_FILE=compose.yml:compose.nginx.yml` (set by `./init.sh <domain> <email> nginx`) binds Caddy to `127.0.0.1:8088` over plain HTTP and trusts nginx's `X-Forwarded-*`; `nginx-site.conf` is the matching nginx site.
- Backups: the `backup` compose service (`Dockerfile.backup`: postgres:17-alpine + rclone; `backup/schedule.sh` → `backup/dump.sh`) dumps daily at `BACKUP_TIME` (`BACKUP_TZ`) into `infra/production/backups/`, keeps `BACKUP_KEEP_DAYS` (14), copies to `BACKUP_RCLONE_REMOTE` when set (rclone env config `RCLONE_CONFIG_*` in `.env`), and is unhealthy when the last good dump is > 25 h old. `deploy.sh` takes one before migrations (`SKIP_BACKUP=1` skips); `backup.sh` = one now; `restore.sh` stops the service while it restores. Keep scripts shellcheck-clean (CI runs it).
- CD: the `deploy` job in `.github/workflows/ci.yml` runs after api/web/docker pass on `main`, SSHes with a key pinned (`restrict,command=`) to `infra/production/ci-deploy.sh`, which only accepts `deploy <sha>` for a commit on `origin/main`, checks it out, runs `deploy.sh` and waits for the API healthcheck.
